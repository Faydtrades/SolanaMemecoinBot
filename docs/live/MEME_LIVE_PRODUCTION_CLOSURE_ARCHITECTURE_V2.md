## SECTION 1 — Fact ownership and identity

### 1.1 Persistence and capability boundaries

Seven proposed packages are named **Evidence**, **Ledger**, **Authority**, **Execution**, **Runtime**, **Operations**, and **External gates**. These names are planning handles, not new permanent G/T task IDs. Domain ownership below is singular even where a package supplies a shared storage transaction.

A dedicated LIVE economic journal is the durable authority for one fixed domain: chain genesis identity, wallet public key, LIVE mode and schema version. It is separate from collector, PAPER, Shadow and research stores. The Ledger package owns its transaction/integrity protocol; the domain owner in the table owns each fact. Append-only evidence and state-change records feed versioned, rebuildable projections. SQLite WAL, FULL durability, foreign keys, unique economic keys, compare-and-swap state versions and a single fenced writer are required. A second process cannot acquire mutation authority merely because the first process stopped heartbeating. The Operations owner must prove exclusive process ownership/fencing before successor arming; any ambiguous owner blocks mutation. Durable send claims and a wallet mutation lane protect crash windows.

The LIVE producer has its own checkpoint/input journal/outbox, because source processing and economic settlement have different authority. Producer batch state and outbox insertion commit together. Runtime transfers at least once into an economic-journal inbox with a unique canonical source key, commits the inbox, then acknowledges the outbox. A crash at either boundary replays harmlessly. No claim of an atomic transaction spanning two SQLite databases is made. Acknowledged immutable provenance remains addressable after checkpoint compaction.

Admission acceptance, approved amount, exposure reservation and inbox disposition share one economic-journal transaction. Finality resolution, settlement application, position quantity, financial postings and reservation retirement likewise commit atomically or remain unapplied. Durable exit obligations are created in the same transaction that makes acquired inventory usable; a subsequent outbox dispatch can retry. A balance snapshot never independently overwrites these projections. Contradictory evidence is retained and quarantined, not resolved by last-write-wins.

Phase-5 remains non-signing/non-broadcast. Reuse its accepted decoding, route, integer quote, plan and zero-signature simulation contracts through a LIVE adapter; do not reuse its expected inventory or terminal execution journal as custody authority. All LIVE signing/send capabilities reside outside `src/phase5`. DRY is a separate fixed journal domain with an adapter graph that cannot construct a production signer or send client. The deterministic acceptance environment uses the same LIVE domain logic but injected synthetic chain/signer/transport ports and disposable stores.

### 1.3 Immutable identity chain

Use canonical encodings with domain-separated hashes and explicit schema versions. Hashes bind content; database uniqueness enforces economic identity. New policy, amount, process UUID, time of replay or checkpoint generation must never create a second LIVE entry for an already accepted candidate.

| Identity | Binding and generation rule | Stability/change rule |
|---|---|---|
| Producer lineage | Collector identity + original anchor + accepted source/model/parameter fingerprints + output namespace | Stable across maintenance and reboot; changed source identity requires explicit reconciliation, never automatic new lineage |
| Candidate | Existing Phase-4 run/candidate ID plus complete immutable provenance | Stable on replay, restart and RPC refresh; strategy run start time is preserved |
| Admission/trade root | Chain + wallet + LIVE + canonical candidate ID | One accepted economic root per candidate, including across later operating-policy versions; no second accepted amount |
| Approved economic record | Root + side/assets/integer amount + approved policy/version + selected track + candidate reference/time/deadline | Created once on acceptance; rejected/expired candidates do not reserve fake trades; transient denials may be re-evaluated only before original deadline |
| Quote and plan | Economic ID + observed venue/account snapshot IDs + accepted route/quote/plan content | New observation may produce a new version with the same approved amount; old versions remain evidence |
| Final message | Plan ID + exact approved envelope/fee policy + blockhash lease + serialized bytes | Any blockhash, instruction, account, fee or byte change creates a new message and requires new exact simulation and authority |
| Attempt/signature | Parent economic action + monotonically allocated attempt sequence + message ID; signature bound to message | Same-byte rebroadcast is the same attempt/signature. A new message is a new attempt only after prior possibly landing attempts are resolved |
| Settlement | Chain + transaction signature + deterministic component index; one atomic applied transaction group | Stable on repeated observations; provisional/partial metadata creates no partial applied fill; finalized failed transactions can still post actual fees |
| Position | BUY trade root + acquired mint + ownership domain | Stable through restart, settlement updates, partial reductions and SELL retries; quantity is a projection, not an ID |
| Exit binding/obligation | Position ID + fixed selected track/policy binding; one active full-reduction obligation for supported policy | Trigger provenance is immutable; retries do not create another independently sized obligation |
| SELL action | Obligation ID + immutable authorized quantity for that action + action ordinal | Attempts retain that quantity. After a proven finalized reduction, any remaining attributed units get a linked residual action; never resell original quantity blindly |

Canonical chain: candidate -> admission/root -> immutable LIVE amount -> venue snapshot/quote -> plan -> final message -> exact simulation/authority -> signed attempt -> send claim -> finalized settlement -> actual position -> selected exit binding/obligation -> SELL action/attempt -> settlement/retirement. Every child stores its parent IDs and content digests. RPC observation IDs and process generations are evidence only and cannot serve as economic duplicate keys.

A candidate has at most one accepted LIVE BUY root. V1 may enforce a maximum of one concurrently open LIVE position as a policy/runtime admission limit, including denial while an unresolved acquisition still reserves capacity. Core identity, ledger, settlement/accounting, risk/reservation, persistence/reconstruction and exit state remain position/mint scoped so later multi-position support does not require redesigning the core. Do not implement concurrent multi-position execution in V1. A persistent mint lock also respects accepted winning-candidate suppression. Distinct mints and positions remain independently identified across subsequent trades. Wallet mutations are serialized, with reductions taking priority. BUY retries retain amount and original ENTRY deadline. SELL retries retain the protective obligation and re-check actual remaining inventory. No historical candidate/root tombstone is removed merely because the position closed.

LIVE requires a separate economic contract because these accepted Shadow facts cannot be resized.

**Non-landing contract.** Evidence owns a bounded, read-only resolver for the exact attempt; Ledger owns adjudication. Before an attempt may be sent, store its chain identity, finalized lower anchor, recent blockhash and last-valid block height. After a send claim, PROVEN_NON_LANDED requires a finalized root beyond that height plus one reviewed proof profile that guarantees complete historical coverage for the exact signature and validity interval. A profile may use an explicitly complete historical-signature service, or bounded enumeration of every produced canonical block in the interval while accounting for skipped slots and missing/pruned pages. Bind endpoint capability, context and coverage to the evidence. A cache-only/null status, incomplete history, provider disagreement or unsupported completeness remains UNKNOWN. Evidence implements and tests this per-attempt adapter; it does not build a general chain indexer or archival platform. A valid exact finalized transaction is stronger positive evidence and avoids the absence proof.

This conservative project policy adds historical completeness to expiration evidence. Solana exposes `lastValidBlockHeight`; cache-only status searches do not cover arbitrary history, and a null transaction response does not prove non-landing. See [confirmation and expiration](https://solana.com/developers/cookbook/transactions/confirmation), [signature-status scope](https://solana.com/docs/rpc/http/getsignaturestatuses), and [transaction retrieval](https://solana.com/docs/rpc/http/gettransaction). No chain RPC was called for this design. RPC trust assumptions and finalized-history availability must be tested/declared by Evidence; “two null responses” is not a completeness certificate.

### 2.3 Settlement, funding and supported custody shape

Use a dedicated Solana trading wallet. It may also be visible/imported in Phantom, but unattended trading must never depend on Phantom approval. The later production path uses a separately authorized local autonomous signer; private key/seed remains local only and never enters Git, prompts, logs or evidence. No key access or signer capability is authorized by owner acceptance or G000. Opening baseline is taken at an explicit finalized cut before arming and inventories wallet lamports, relevant token accounts/mints/programs/owners and their rent/native reserves, including absent accounts. V1 requires a known wallet, known SOL funding and no unsupported/unattributed pre-existing token/WSOL holdings. Recognized supported external holdings must be excluded explicitly from strategy inventory; unknown or unsupported holdings deny arming. The initial route profile continues to require absent WSOL for native capital recycling. Unexpected token programs, delegated/frozen accounts or unsupported extensions deny that shape before signing. Capital amounts and exit-track choice still require separate owner inputs.

For each finalized transaction, bind actual pre/post balances and account lifecycle to the exact approved message and transaction metadata. Attribute principal, received/sold base units, quote proceeds, actual transaction/priority fees, ATA rent lock/refund and WSOL creation/wrap/sync/close separately. Native-account lamports and wrapped-token units are linked representations and must not be counted twice. Failed transactions can charge fees without executing the planned swap; their actual metadata still posts. A partially received metadata response is not a partial trade. Any real residual inventory after a finalized reduction remains owned and protected; no rounding/dust write-off silently closes it.

Spendable funding is a vector: finalized native SOL available for principal; finalized WSOL units in each account; attributed base-token units; locked/refundable rent; accrued actual fees; principal reservations; pending-attempt worst-case costs; and reserved exit fee/rent headroom. Risk consumes this vector with a version, then final-message approval revalidates the exact accounts and cost bounds. A reservation is an encumbrance on reconciled funding, not another balance owner. Already posted fees are audit components reflected in reconciled balances; funding subtracts only outstanding encumbrances, never paid fees a second time. An external transfer is an adjustment with evidence and classification, not a profitable fill. External withdrawals invalidate affected authority immediately when detected; the supported operating policy prohibits concurrent manual wallet mutation while armed.

Accepted PumpSwap plans transfer the full BUY quote amount from native SOL and close a WSOL account only when that plan created it (`src/phase5/shadow_unsigned_plan_simulation_v0_1.py:1068`, `:1129`). Therefore the initial supported automatic capital-recycling path uses absent WSOL -> transient WSOL -> close -> actual native SOL settlement. Existing/retained WSOL is explicitly accounted as WSOL and is not credited as spendable native SOL. Starting with a pre-existing WSOL account is denied for this initial entry profile, even if wallet totals look sufficient. If such a shape appears while a real position is already open, Ledger quarantines unexplained changes and Authority may allow a fully evidenced reduction under the accepted plan, retaining its actual WSOL proceeds separately. Operations owns the alert/recovery runbook; restoring a supported wallet shape requires a separately authorized external action or future separately reviewed capability. No automatic unwrap is invented here. Deterministic acceptance must prove both normal native recycling into a second trade and the explicit retained-WSOL denial without losing existing protection.

One shared funding vector accounts for position-scoped reservations and obligations; V1's one-open-position limit is an admission policy rather than a singleton economic-state schema. Reserve exit headroom for the supported open position and its serialized exit, including bounded failed-attempt costs. No numerical capital, fee cap or FINAL-A/FINAL-B/SENS-C choice is assigned here. Authority validates required policy fields and denies arming until the owner supplies them; engineering uses deterministic synthetic values in fixtures. Exhausted fee headroom is a concrete alerted protection limitation, not permission to overspend or drop an obligation.

### 2.4 Selected exits and producer lifetime

It must not substitute fill price/time, add three tracks as a portfolio, or import hypothetical Shadow inventory. Actual finalized acquisition controls activation and units only. ### 2.5 Exact boot dependency order and barriers

1. Start only the declared capability mode. Acquire proven exclusive process ownership/fence; load durable hard-stop and public policy/grants. A watchdog restart cannot arm a stopped process.
2. Audit LIVE journal identity/schema, integrity, foreign keys, evidence bindings and incomplete transactions. Restore only committed state. Economic corruption blocks all mutation and escalates.
3. Perform a bounded probe of original producer/source identity and the last published checkpoint/tail, recording source coverage/health. Identity, availability or recovery-budget failure records ENTRY_PAUSED and continues independent economic recovery when that journal is intact. Bulk source/feature replay runs separately and may not delay steps 4–9; step 10 waits for its successful completion.
4. Restore chain/wallet opening baseline and obtain coherent current public account/chain observations. Validate chain identity, freshness, account programs and UTC bounds. No capacity is yet usable.
5. Reconcile every signed/claimed/pending attempt to evidence or UNKNOWN. Reconcile known external adjustments; never treat a missing local response as an unsent transaction.
6. Atomically replay/apply finalized settlements, actual inventory and financial postings; compare projections with fresh accounts. Unknown attribution blocks the affected/shared resource scope.
7. Rebuild reservations/exposure and exit headroom from attempts plus real positions. Mark capacity usable only for reconciled unencumbered resources; entry usability additionally requires later barriers.
8. Restore each position's selected-track binding, acquisition/knowledge cuts, controller state, due timers and outstanding obligation. Materialize already-due fallback obligations before new candidate processing.
9. Open **PROTECTIVE_READY** only if steps 1–8 provide intact relevant inventory/funding, exclusive authority, policy permitting reduction, no unresolved conflicting wallet attempt, and no hard stop. Source producer health may remain denied. Start protected observation/timer/reduction scheduling first.
10. Recover producer inbox/outbox and exact timer fences, verify fresh source coverage, supported reconstruction profile and original candidate deadlines. Open **ENTRY_READY** only after PROTECTIVE_READY (or proven no positions), healthy source/producer/clock, approved entry policy, reconciled capacity and no unresolved wallet-wide uncertainty.
11. **SIGN_READY** is per message, never a boot-global flag: valid relevant ENTRY or reduction authority, current ownership/stop/policy, exact plan/message simulation, correct signer, lease/deadline and versioned resource reservation. **SEND_READY** rechecks authority/deadline/lease against that immutable signed attempt immediately before a durable send claim. A refreshed blockhash requires a new message/simulation/signature under the replacement rules.

No mode switch converts a DRY journal into a LIVE journal. Operator arming in LIVE must follow the appropriate external gate and this full boot contract. Readiness loss after boot revokes the relevant barrier immediately; already broadcast transactions remain subject to reconciliation because they cannot be recalled.
