## A1 — Exclusive ownership, final dispatch fence and durable stop/restart control

`operations_ownership_v0_1.py` adds one finite Operations control row, separate from Ledger/Authority. Explicit initialization creates the store; reopen only validates/reads existing exact schema, domain/config binding and finite state. The current owner binds the Ledger economic domain (genesis/wallet/mode), full Ledger binding digest, durable generation, process identity and fresh nonce. Capabilities are process-local and nonserializable; close, replacement, stop, exhaustion, wrong configuration or lost/replaced store deny current use. The trusted composition host must select one canonical Operations store per wallet/economic domain. It must not create competing stores or bypass the owned composition; this is not a sandbox against arbitrary host code.

Acquisition is exclusive by durable transaction/CAS. Explicit replacement requires the current generation, advances it and consumes another attempt. Initial acquisition also consumes one attempt. The retained budget identity, attempt count, window start, next eligible time, last control time and configured finite count/window/backoff are durable. Backoff and clock regression deny. A nonexhausted window can roll over; after the configured limit is reached, the next acquisition denies and durably latches exhaustion before a later window can replenish it. Exhaustion revokes the old fence and never expires. Only explicit `operator_reset(expected_generation=..., now_us=...)` changes the budget identity, clears Operations stop/exhaustion and invalidates prior ownership; it never acquires an owner. Stop is durable across reopen and child replacement. No heartbeat or elapsed liveness creates permission. These are configured synthetic bounds, not measured production timing or a frozen operating envelope.

The additive typed `ownership` argument on actual Runtime, Q2 `sign_exact` and Q3 `send_exact` is the exact affected compatibility surface. Runtime checks current ownership after its clock and before new admission/preparation; a stopped/stale root returns `OPERATIONS_HELD`. Both actual dispatches then independently reacquire/validate current Operations identity after the final trusted provider callbacks and hold the Operations SQLite writer transaction across the key call or claimed transport call. The same Q3 guard covers original REBROADCAST. This closes the stale-precheck race while retaining the existing fresh Authority, exact message, source and Ledger guards. SIGN denial retains the consumed/held attempt; post-claim SEND denial retains the exact signature and original possible-send UNKNOWN state.

Control transitions use that same serialization boundary. A stop/takeover cannot commit through an in-flight dispatch. The API uses finite nonblocking database contention: a busy control request has **not** committed and the trusted caller must explicitly retry after the bounded call finishes. Already dispatched work cannot be recalled and still requires original reconciliation. A stale process may remain alive or hold the existing Ledger writer lock; A1 proves mutation fencing, not process termination or replacement availability. Operator stop/reset and generation-qualified replacement are explicit trusted host/operator operations, never automatic child/heartbeat behavior. No watchdog, restart loop, service or task installation exists here.

Safe reads remain available through `OperationsStore.snapshot()` and the original Ledger audit/consumer reads while stopped. A1 does not add a second Runtime model or bypass economic recovery through `step`. No Operations control receives a Ledger/Authority handle; the focused test proves an existing Authority hard-stop, policy and grant survive Operations stop/reset/reacquisition unchanged. Omitted ownership preserves the established standalone engineering interfaces. The accepted pre-Operations C4 cold factory bypasses `__init__`, so the Runtime class retains the explicit unowned default; A1 makes no startup/readiness claim for that interface.
